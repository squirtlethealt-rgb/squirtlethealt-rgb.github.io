01 Purpose & Scope

This document specifies requirements for a browser-based LMS unifying The Sky Explorers' Python Programming and Data Science Level 1 courses under one platform, with the Electronics and Drone Program curricula onboarding in later phases. The platform must serve students directly, give facilitators a way to run and monitor live sessions, give parents visibility into progress, and give admin/ops a way to manage cohorts across schools.

The Drone Program is explicitly out of scope for this version — hardware platform (DroneBlocks / CoDrone EDU / Tello) is undecided, and drone-specific block-coding UI is deferred until that decision closes.

03 Functional Requirements

3.1 Authentication & Onboarding

Flag: first-name + self-chosen secret key collides across a class and offers no real access control. Recommendation below changes the original ask slightly — confirm before build.

IDRequirement
REQ-AUTH-01Facilitator or admin creates the student record at cohort setup: first name, grade, school, cohort. System generates a unique, memorable secret code (e.g. two-word phrase) — not user-chosen — to avoid collisions.
REQ-AUTH-02Student logs in with first name + assigned secret code; system disambiguates by cohort/school if first names repeat.
REQ-AUTH-03Facilitator and admin accounts use standard email + password (or magic link) auth.
REQ-AUTH-04Parent account links to a student via a code shared by the facilitator/school, not by searching student records directly.
REQ-AUTH-05No student personal data beyond first name, grade, and school is collected at registration (DPDP Act minors' data consideration — see §4).

3.2 Course & Session Navigation

IDRequirement
REQ-CRS-01Student sees only their enrolled course(s) and current/past sessions; future sessions are locked/hidden to preserve reveal-based mechanics (e.g. Mystery Build).
REQ-CRS-02Each session has exactly two files: an Activity file (in-session work) and, when assigned, a Homework file — presented as tabs, not a folder tree.
REQ-CRS-03Facilitator can advance/unlock the next session for their whole cohort at once.

3.3 Python Interpreter Environment

IDRequirement
REQ-PY-01Python executes client-side via Pyodide (WASM); no code is sent to a server to run.
REQ-PY-02Each student's virtual filesystem persists per session; Activity/Homework files auto-save on pause (not on explicit save) to survive interruption.
REQ-PY-03Saved state syncs to the backend so a student can resume on a different device (school → home).
REQ-PY-04The Mystery Build file is a distinct, protected file type: it persists and accumulates across all 26 sessions and is never visible in a future/locked session's view.
REQ-PY-05On run, the currently-executing line is highlighted; on an error, the failing line is highlighted (Thonny-inspired). This is a lightweight visual cue, not a full stepper — see §9 for the deferred step-through debugger.
REQ-PY-06Editor and output sit in one fixed split (code above, output below); no REPL/command-echo concept — output only, nothing to type or learn beyond code and Run.
REQ-PY-07Pasting code into the editor is disabled (Activity, Homework, and Mystery Build files alike) — students must type code themselves; this applies to the Data Science notebook cells too (see REQ-DS-01).
REQ-PY-08Exception: approved code snippets on lesson pages get a dedicated "Insert" button that inserts directly into the editor via the app itself — not the OS clipboard. Regular copy/paste (Ctrl+V) remains blocked everywhere, since clipboard content carries no reliable origin — it can't be trusted to distinguish "copied from our site" from "copied from anywhere."

3.4 Socratic Error-Hint Assistant

IDRequirement
REQ-HINT-01After 10s of no keystrokes following an edit, a callout may appear near the likely error line.
REQ-HINT-02The callout asks a guiding question about that line (Socratic) — it never states the bug or the fix.
REQ-HINT-03Student must run the code themselves and read the actual error before any further hint is offered.
REQ-HINT-04Hint frequency fades by milestone: full scaffolding in Milestones 1–2, reduced by Milestone 4, silent from the peer-testing sessions onward.
REQ-HINT-05Callout uses a restrained 2–3 color semantic palette and is sized/positioned using golden-ratio proportions (~1:1.618) relative to the editor pane.

3.5 Data Science Notebook Environment

IDRequirement
REQ-DS-01Notebook-style environment (cell-based, mixed markdown + code) running on the same Pyodide runtime as the Python course for consistency.
REQ-DS-02Same Activity/Homework file pattern as Python, one notebook per cycle.
REQ-DS-03Final project notebook (Appendix C, Cycle 12 Showcase) persists as one continuously-built file across cycles, not per-cycle snapshots.
REQ-DS-04Where a student has already taken Python Programming, Pandas/NumPy content in Cycles 4 & 9 is framed as "building on what you know," not re-taught from zero.

3.6 Homework & Submissions

IDRequirement
REQ-HW-01Homework file is assigned by the facilitator at end of session and becomes editable for the student until the next session unlocks.
REQ-HW-02Facilitator sees completion status per student per homework file (not started / in progress / submitted).
REQ-HW-03Facilitator can leave inline comments on a homework file, tied to specific lines/cells.

3.7 Facilitator Dashboard

  • Roster view per cohort with live status (active now / idle / not started today).
  • Ability to peek at a student's current Activity file read-only during a live session.
  • Homework completion overview across the cohort.
  • Session pacing controls (unlock next session, reopen a locked one for a student who missed a class).

3.8 Parent View

  • Read-only: sessions completed, homework status, upcoming session dates.
  • No access to a child's live code or ability to edit anything.

3.9 Admin/Ops Console

  • Create schools, cohorts, assign facilitators.
  • Cross-cohort reporting (completion rates, homework turnaround) for internal review and school-facing reports.
  • Manage course content versioning as curricula are updated between cohorts.

04 Non-Functional Requirements

AreaRequirement
PerformancePyodide runtime cached after first load; target <3s cold start on a typical school Chromebook, near-instant on repeat visits.
Offline behaviorOnce loaded, code execution works without connectivity; saves queue and sync when connection returns.
Device supportMust work on low-spec school Chromebooks/tablets and personal laptops/phones — no install required, browser-only.
Child data privacyMinimal data collection (first name, grade, school only); registration facilitator-initiated to satisfy guardian-consent expectations under India's DPDP Act for minors' data.
AccessibilityLegible type scale for ages 11+, visible focus states, color choices not solely conveying meaning (relevant directly to the error-hint palette in REQ-HINT-05).

05 System Architecture

Proposed stack: Next.js frontend hosted on Vercel, with serverless API routes for auth, file sync, and reporting. Pyodide runs entirely client-side. A managed Postgres instance (e.g. Neon/Supabase, both play well with Vercel) stores users, cohorts, progress, and file snapshots.

07 Visual Design Direction

Base UI stays calm and legible — kids need to focus while coding — with the bold pop-art energy reserved for reward moments: session-complete screens, the Mystery Build reveal, badges. Per-course accent color and icon (not a full re-theme) so a student can tell Python from Data Science at a glance.

Error-hint UI specifically: golden-ratio proportions for the callout's size/placement against the editor pane; a restrained 2–3 color semantic palette (not the full pop-art spectrum) so the hint reads as calm guidance, not an alarm.

Run controls: 3–4 large labeled buttons (Run, Stop, and later Step) rather than a dense icon toolbar — no menu bar, no icons a student has to learn the meaning of first.

08 Open Decisions

Secret-code scheme: recommend system-generated unique code over user-chosen, to avoid class collisions and give a real access boundary. Needs your sign-off before build.

Backend/DB provider: Neon vs Supabase vs other — both integrate cleanly with Vercel; pick based on whether you want built-in auth (Supabase) or prefer to roll your own (Neon + custom auth).

Notebook UI library: build a lightweight custom cell-based notebook vs adapt an open-source one (e.g. Jupyter-lite) — affects Data Science build timeline.

Facilitator training: not a platform requirement per se, but the Socratic hint model and Mystery Build secrecy only work if facilitators are trained/dry-run before launch.

09 Future Scope

  • Drone Program integration once hardware platform (DroneBlocks / CoDrone EDU / Tello) is finalized — will need a block-coding editor distinct from the Python/notebook environments.
  • Full line-by-line step-through debugger (Thonny-style Step Over/Into) inside the Pyodide runtime — meaningfully harder than the current/error-line highlight in REQ-PY-05, treated as its own phase-2 feature rather than a v1 requirement.
  • Electronics curriculum onboarding.
  • Cross-course achievement/badge system leveraging the pop-art visual language.
